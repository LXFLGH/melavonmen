把 WebView2 壳搬上 macOS：WKWebView 移植实战与三轮踩坑

2026-09-25 · C++ / macOS / WKWebView

我的农场游戏 FCN（C++17）前端是纯 JS/HTML/CSS，Windows 上靠 WebView2 承载，桥接协议复刻 pywebview 的 js_api。架构上桥接分发早已下沉进核心库（CLI / GUI / HTTP 三端共用一张 56 方法分发表），所以移植 macOS 理论上只需要换一个"壳"。理论上。

壳层对齐

WKWebView 与 WebView2 角色对等，映射关系如下：

Windows（WebView2）macOS（WKWebView）
CreateCoreWebView2EnvironmentWKWebView + loadRequest
PostWebMessageAsJsonevaluateJavaScript
window.chrome.webview.postMessagewindow.webkit.messageHandlers.*
虚拟主机 https://app.fcn自定义 scheme fcn://app + WKURLSchemeHandler
Win32 消息循环 + WM_TIMERNSApplication runloop + NSTimer

CMake 侧用三平台分支让编译器自动选壳：if(WIN32) 编 WebView2 版，elseif(APPLE) 启用 OBJCXX 编 WKWebView 版，业务桥接层零改动。

三轮踩坑

第一轮：回传协议错位

症状是按钮全无反应、地图不渲染。插桩后发现 C++ → JS 的响应全部在 JS 端抛异常：我的注入脚本给 __fcnReceive 加了 JSON.parse，但 evaluateJavaScript 传入的本来就是对象字面量——JSON.parse(对象) 被强转成 "[object Object]" 直接 SyntaxError。Windows 版没这问题是因为 PostWebMessageAsJson 的 e.data 就是对象，shim 不做 parse。照抄协议时语义要对齐，不能只对齐"长得像"。

第二轮：资源回落与原生对话框

两个独立问题一起爆发：

  • 非默认主题机器人不显示——磁盘模式最初用 loadFileURL 直读主题目录，它拦不到子请求，主题缺的共享资源不会回落到内置 frontend/。改成磁盘与资源包模式统一走 fcn://app scheme handler，服务链与 Windows 虚拟主机拦截同源。
  • 新建文件按钮无反应——WKWebView 默认不实现 alert/confirm/prompt（静默 no-op，prompt 恒返 null），前端 9 处原生对话框全部失效。WebView2 自带默认对话框所以从未暴露。需要自己实现 WKUIDelegate 三个回调。

第三轮：Safari 15 没有 roundRect

终端风主题"初始化失败"、其他主题机器人不渲染，日志里每帧刷 TypeError: ctx.roundRect is not a function。roundRect 要 Safari 16（macOS 13）才有，而 macOS 的 WebKit 版本被系统锁死，macOS 12 上无解。最终在壳的桥接注入脚本里内置 polyfill（document-start 注入，先于主题 JS，有原生实现自动跳过），一处修好全部主题。

一点体会

跨平台移植 90% 的工作量在最后 10% 的平台差异里，而且差异的形态五花八门：有协议语义的、有内存管理约定的（WKWebView 的 delegate 全是 weak）、有浏览器能力差异的。

诊断基建是这轮最大的收益：JS 侧 onerror/unhandledrejection 上报通道 + C++ 侧求值失败日志 + 回程往返探针，全部落进一个 gui_bridge.log。三轮 bug 都是靠它几分钟内定位的——没有这套东西，"点了没反应"这种问题能查一天。
