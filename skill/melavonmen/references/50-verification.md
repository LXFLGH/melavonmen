# 验证门禁：能自动检测的自动检测，无法检测的明确披露

## 每次改码必须执行

1. 运行受影响功能的测试/构建：唯一成功标准为`0 failed`、正确退出码；日志要完整保留，不用`| tail`代替失败现场。
2. [tools](90-tooling.md)中校验`index/schema/symbols/drift`，涉素材时加`assets`；Doc/Wiki缺失的任务按当前状态门禁决定如何处理，不滥用工具。
3. 各文件的数量、行号、hash、参数/返回类型都必须能从源码或命令复现；记入`doc/changes/<task>.json`，虚警结论写入`ruled_out[]`并附依据。
4. 检查所有已变更代码是否关联到需要更新的合同、Wiki页面及索引；若没有深度Wiki页，则先建对应模块页再宣称受影响范围已覆盖。
5. 清楚列出`errors, warnings, unverified, tests_not_run`。**校验程序0错误不证明业务语义正确**；对于非Python语言，默认符号验证只检查源码SHA，签名需合适的语言解析器/构建系统或人工复核。
6. 若本回合生成或替换了素材图，额外核对：清单条目数 == 交付图片文件数、普通素材`sprites == 1`、精灵表`sprites`==atlas帧数且帧矩形不越界、逐帧源文件存在、尺寸/hash与文件一致、`assets/_raw/`原件在位、无未申报的合图。缺一项即未完成，不得以“图看着没问题”代替。

## 自检顺序

`validate_index.py` → `validate_schema.py` → `validate_symbols.py`（Wiki存在时） → `validate_assets.py`（涉素材时） → `detect_doc_drift.py`（Git工作区） → 项目测试 → 文档一致性复核。

**增量同步不会机械要求每次都修改无关Doc**：如果只改日志文字，合同不变，记录“无合同影响”和可证依据即可；如果形参、返回值、结构或行为变化，必须回写合同和Wiki。

## 结束条件

`0 failed` + Doc目标合同与实现一致 + Wiki事实未过期 + 索引完整 + 素材清单与文件一一对应（涉素材时） + 重大阻断归零 + 用户交付可验证 → 可报告完成。若没有工具/依赖/权限，明确剩余工作，不能写“已验证”或“零漂移”。用户只请求设计方案则无需假装执行代码测试。
