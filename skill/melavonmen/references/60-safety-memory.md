# 红线、证据和记忆连续性

1. 用户提供、AI绘制、人工制作的资源与素材一律不可擅自删除、替换、重绘覆盖；即使看似占位也视为受保护。处置前列逐文件清单、影响与回滚措施，等待明确确认。
2. 素材图**一素材一文件**：每个贴图/图标/立绘/瓦片单独成文件，禁止多主题拼版、UI 图集、contact sheet 或靠坐标切图的隐性混装。**精灵表例外**：同动作序列帧/同用途图块集可多帧合图，但必须有 atlas 元数据、逐帧源文件、清单登记`kind:"sprite_sheet"+sprites+atlas+source_files`。生成原件留`assets/_raw/`，交付件放`assets/<category>/`，逐文件登记尺寸/sha256。细则见[素材交付](65-asset-delivery.md)。
3. 生成新素材同样受“不覆盖”约束：同名文件先比对（尺寸/哈希/用途），要么另起名，要么先取得确认；不得以“重出高质量版本”为名覆盖既有素材。
4. 破坏性操作（删除/覆盖/移动重要文件或素材）必须先确认；优先可逆操作与版本备份，不可静默“清理”。
5. 代码中的用户可见文本应走项目i18n资源，不硬编码；命令/代码引号按项目语法保持有效。
6. 多Agent互斥编辑同一个文件，Doc和Wiki页同样受文件所有权保护；共享总索引由协调者统一合并。
7. token、密码、密钥等敏感凭据不得进入仓库、日志、提交、文档；使用时遵循最小权限，不在对话中输出。
8. 陌生项目先只读扫描和受影响面评估，现有Doc/Wiki先读索引；不得未经验证把旧记忆当作当下源码事实。
9. 数字、签名、行号、版本、hash、调用者、测试结论必须有可复现的证据；被证伪的误报应带证据记录在变更单，防止反复排查。
10. 函数签名/形参/返回类型、数据结构、依赖、行为变化后，**同一工作回合**反向更新受影响Doc/Wiki及索引；关键冲突先在Doc记录解决方案再写代码。

记忆层级：任务会话 → 追加式当日日志 → 经复核的长期MEMORY.md；Doc持有目标契约，Wiki持有现实源码事实。记忆不覆盖用户新指令、源码和实际验证证据。

交接包：task_id、state、revision、受影响源码/Doc/Wiki、未验证问题、测试记录、下一步。严禁凭“已交接”就把未验证项标成verified。
